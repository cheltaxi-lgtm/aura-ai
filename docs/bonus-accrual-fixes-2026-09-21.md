# Исправления начисления бонусов — 21 сентября 2026

Статус: **PARTIAL — изменения внесены, проверка PostgreSQL заблокирована локальной средой**. Production, пользовательские балансы и рабочая БД не изменялись; миграция 158 не применялась. Исходный аудит: [bonus-accrual-audit-2026-09-21.md](bonus-accrual-audit-2026-09-21.md).

## Условие фактического посещения

Ежедневный бонус: 5 рун после доверенного браузерного действия (pointer/keyboard или нажатия кнопки) на видимой странице. Само открытие страницы, фоновая вкладка, таймер, опрос статуса и событие visibilitychange начисление не вызывают. Синтетические события, включая `.click()` по кнопке, игнорируются. Правило действует в карточке кабинета, на главной и в магазинах рун.

Сервер допускает одно начисление на профиль за скользящие 24 часа, использует время PostgreSQL и записывает изменение баланса и журнал одной транзакцией. За пропущенные дни ничего не накапливается: даже после месяца отсутствия следующее посещение приносит только один бонус. Несколько вкладок должны сходиться к одному начислению через условный UPDATE; тест конкурентности подготовлен, но пока не выполнен на БД.

Граница гарантии: `isTrusted` и видимость — правила штатного клиента, а не доказательство присутствия человека на сервере. Авторизованный пользователь технически может автоматизировать прямой POST. Сервер всё равно ограничивает частоту и владельца. Для строгой защиты от автоматизации потребуется отдельно выбранная антибот-политика; подмена её полем `visited: true` ничего не доказывает.

Условие посещения относится к ежедневному бонусу. Стартовый подарок, заслуженные достижения и оплаченная подписка имеют собственные основания; начисление по подтверждённой оплате нельзя зависеть от открытой вкладки.

## Исправления по аудиту

| Пункт | Изменение |
| --- | --- |
| B01 | Лимит запросов 10/мин вместо 1/сутки; новый namespace лимитера не наследует старую блокировку. Право на бонус определяется атомарным состоянием БД. Ошибка записи откатывает начисление. |
| B02 | Дни общения нормализуются в UTC текстом, вычисляются текущая и максимальная историческая серии. Выдаются все заслуженные числовые достижения; popup сохраняет прежний одиночный контракт. |
| B03 | Статус платежа, бонус, продление доступа и оплаченная история фиксируются одной транзакцией. Ошибка оставляет заказ доступным для повтора. |
| B04 | Новая email-регистрация требует подтверждения почты для стартовых, ежедневных и achievement-бонусов. App-заголовок больше не отключает CAPTCHA регистрации. Старые аккаунты сохранены без массовой блокировки. |
| B05 | OAuth больше не объединяет аккаунты автоматически только по email. Требуется вход и явная привязка; токены подтверждения почты используют отдельный производный ключ, audience и привязку к аккаунту/email/token_version. |
| B06 | Сумма бонуса подписки фиксируется при создании заказа вместе с ценой. YooMoney привязан к конкретному orderId; повтор уведомления не повторяет выдачу и партнёрское начисление. Старый label без orderId допускается только при однозначном заказе. |
| B07 | В кабинете есть карточка бонуса, время следующего получения и повторная отправка подтверждения. Исправлены сообщения об ошибках; уведомление на главной центрируется без конфликта transform. |
| B08 | Ручная выдача администратора использует UUID операции; повтор возвращает прежний результат, изменение суммы/описания с тем же UUID отклоняется. |

Отключено новое вознаграждение за чувствительные ключевые слова `brave_question`; ранее выданные достижения и средства сохранены. Уточнены правила подарка на профиль и серии общения по UTC. Ошибка общего кредитования больше не скрывается успешным возвратом старого баланса.

## Порядок завершения и рекомендации

1. Восстановить тестовую PostgreSQL, применить штатные миграции и выполнить `node node_modules/vitest/vitest.mjs run tests/invariants/bonus-accrual.test.ts`. Проверить миграцию 158 на копии схемы перед выпуском. Она фиксирует бонусы старых pending-заказов по текущей настройке, поскольку исторический курс не сохранён.
2. Выполнить полный сценарий регистрации → письмо → подтверждение → фактическое посещение в Next.js с тестовой БД и почтовым стендом; затем обновить независимые review evidence.
3. Перед выпуском выполнить read-only сверку старых успешных подписок и бонусного журнала. Старые `succeeded` заказы автоматически не проигрываются: это могло бы повторно продлить доступ. Компенсации должны быть отдельными идемпотентными операциями после подтверждения недостачи.
4. Контролировать дубли ежедневных бонусов, отрицательные балансы, failed fulfillment, долю подтверждения email и доставку писем. Срок сгорания бонусов и единый лимит на человека не вводились: это отдельные продуктовые правила, текущая единица учёта — профиль.

Деплой и применение миграции к рабочей БД не выполнялись.
