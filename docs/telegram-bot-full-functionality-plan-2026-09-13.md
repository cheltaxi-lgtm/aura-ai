# План полнофункционального Telegram-бота Zovus

Дата: 13 сентября 2026. Статус: план, реализация не начата.

Рабочее допущение: основные клиентские функции доступны внутри Telegram. Переписка служит для вопросов, быстрых действий и выдачи результатов; существующий Mini App — для сложных форм, диаграмм и большого архива. Аккаунт, баланс, история, память и расчёты общие с сайтом. Обычная ссылка на сайт сама по себе не считается завершённым Telegram-сценарием.

Полнофункциональность означает законченный путь: вход → выбор услуги → ввод данных → понятная стоимость → подтверждение → результат → уточнение → сохранение и повторное открытие. Пользователь также может восстановить прерванную операцию, обратиться в поддержку и управлять своими данными.

**3. КОНТРАКТЫ — что зафиксировать перед реализацией**

- **Источник данных.** Postgres сайта остаётся источником аккаунта, денег, сессий и отчётов. SQLite бота хранит Telegram-состояния, inbox и доставку. Во всех новых bridge проверяется владелец; Telegram ID поступает через доверенный transport, а не из непроверенного клиентского тела. Сохранить существующую модель привязки и не включать отключённые способы входа попутно.
- **Доступность продукта.** Расширить `/api/internal/bot/modules` полями `mode: native | miniapp | disabled`, `actions`, `disabledReason` и безопасным назначением открытия. Старые `native`/`url` сохранять до обновления всех потребителей. Учитывать серверные feature flags. Наличие backend-функции само по себе не означает доступность действия пользователю.
- **Продолжение разговора.** Расширить существующий `POST /api/internal/bot/chat`: сохранить `telegram_user_id`, `session_id`, `message` и добавить `clientEventId`. Повтор того же события возвращает сохранённый ответ либо статус его обработки. Ответ содержит идентификаторы сессии/операции, состояние и реальную стоимость/баланс, согласованные с текущим `ChatOrchestrator`. Не вводить вторую тарификацию чата.
- **Долгие работы.** Использовать существующую очередь: `operationId → jobId → resultId`. Согласовать состояния ожидания, выполнения, готовности, ошибки и возврата с текущими job DTO. Повтор API/update не запускает новое оплачиваемое задание. Выход в меню прекращает форму; отмена принятой работы выполняется только там, где её поддерживают сервис и правила возврата.
- **История.** Добавить к текущему history-запросу `cursor`, `limit`, `product`; отдавать `items`, `nextCursor`, стабильные `resourceType/resourceId`. Существующие `sessionId` сохранить. Для отчётов, которые не являются сессиями, не придумывать фиктивный session ID. Списки и детали проверяют владельца.
- **Оплата.** Сервер создаёт заказ ЮKassa с неизменными владельцем, пакетом, суммой и валютой; стабильный `request_id` повторно возвращает тот же checkout. Начисление выполняется только после подтверждённого статуса провайдера и остаётся идемпотентным. Отмена окна оплаты не подтверждает и не опровергает серверный успех. Компенсация рун за сбой услуги связана с исходным списанием.
- **Согласия и профиль.** Передавать и сохранять отдельные решения по условиям сервиса, памяти и уведомлениям. Нативные формы сохраняют продуктовые подтверждения сайта, включая `aiDataUseAcknowledged` там, где он требуется. Данные рождения включают дату, известность времени, место/координаты и корректный IANA-пояс; не подставлять придуманное время для Натала/HD. Проверить удаление pending navigation, заданий и Telegram-состояний, а также повторную регистрацию во время удаления.
- **Mini App.** Сервер проверяет подпись и свежесть `initData`; `initDataUnsafe` не авторизует пользователя. Вход остаётся связан с существующей identity, переходы ограничены допустимыми маршрутами. Запуск должен ждать фактической готовности SDK, а не считать задержку загрузки открытием вне Telegram. Основа требований: [официальная документация Mini Apps](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app).

Потребители изменений: бот, Mini App, internal API, общий кабинет, async worker и уведомления. Форматы расширяются совместимо; старые callback-кнопки должны корректно устаревать и предлагать открыть актуальное меню. Переключение платёжного канала не должно ломать ранее начатые заказы.

**4. РИСКИ И ПОРЯДОК ВКЛЮЧЕНИЯ**

| Риск | Как ограничить |
|---|---|
| Повтор списания/начисления при timeout, двойном нажатии или рестарте | Стабильные ID, транзакционные ограничения, сверка с исходным заказом; тест конкурирующих запросов и восстановления. |
| Потеря баланса/истории при привязке двух аккаунтов | Сначала проверить поддерживаемый upgrade. Не объединять автоматически конфликтующие аккаунты. Перенос, если нужен, проектировать с доказательством доступа и отдельной проверкой журналов. |
| Несанкционированные рассылки и возврат удалённых данных | Исправить consent; проверять актуальное согласие при отправке, использовать существующий erasure lifecycle. Не массово менять старые согласия без установления их происхождения. |
| Копирование расчётов/цен и расхождение с сайтом | Переиспользовать общие application services и серверные цены; эталонные проверки при изменении входных данных или расчётных контрактов. |
| Потеря результата между генерацией и отправкой Telegram | Сначала сохранять результат, затем доставлять; действие повторного открытия. Не обещать ровно одну сетевую доставку при неизвестном исходе Telegram API. |
| Плохая работа Mini App на мобильных клиентах | Реальная приёмка SDK, auth, BackButton, клавиатуры, фото, PDF и возврата из свёрнутого окна. |
| Скрытые отказы при зелёном health сайта | Проверять bot `/ready`, авторизованный bridge, очередь и отдельный пользовательский smoke. |

Новые платежи, native chat и новые продуктовые действия включать независимо через существующую систему флагов. Сначала тестовый контур/QA, затем ограниченное включение и общий релиз. При выключении новых заказов сохранять чтение оплаченных результатов и завершение уже принятых работ. Использовать штатный `scripts/deploy-prod.sh`, совместимые миграции и его защиту восстановления; состояния денег и jobs нельзя откатывать простым возвращением старой SQLite.

**5. ПРОВЕРКА И КРИТЕРИИ ГОТОВНОСТИ**

До запуска проверок подготовить отдельный `BOT_DATA_DIR`/`BOT_DB_NAME`, тестовый PostgreSQL и тестовые credentials. `npm test` и особенно `npm run audit` бота могут писать fixtures и применять миграции к настроенной SQLite; их нельзя направлять на рабочую БД.

Существующий быстрый и полный проходы после изменений:

```text
node scripts/ai-harness.mjs --scope telegram --level fast
node scripts/ai-harness.mjs --scope telegram --level full
```

Добавить `tests/invariants/telegram-photo-retry-regressions.test.ts` в Telegram full. До этого запускать отдельно:

```text
npx vitest run tests/invariants/telegram-photo-retry-regressions.test.ts --no-file-parallelism
```

Дополнительные существующие команды по изменённым областям и для общей приёмки:

```text
npm run --prefix telegram-bot audit
npm run test:invariants:db
node scripts/ai-harness.mjs --scope full --level full
```

Не считать отсутствие тестовой БД успешным результатом: для обязательных DB-сценариев требуется ноль skipped. Тест 410 для отключённых Stars сохранить; тест перехода follow-up на сайт обновить вместе с нативным контрактом. Локальные smoke-рендеры и прежние PASS не заменяют реальную проверку Telegram.

| Приёмочный сценарий | Что должно быть доказано |
|---|---|
| Новый пользователь и существующий аккаунт | Понятный вход/привязка, отдельные согласия, восстановление доступа, отсутствие второго стартового бонуса при повторе. |
| Любой платный продукт | Цена → подтверждение → ровно одно списание → сохранённый результат → архив → уточнение; ошибка приводит к понятному статусу и предусмотренному возврату. |
| ЮKassa | Создание checkout, отмена, success/confirm/webhook, повтор кнопки и update, рестарт, возврат и обращение в поддержку. Проверять в тестовом магазине ЮKassa. |
| Возврат к выбранной услуге | После пополнения открывается выбранная услуга/заказ; покупка рун сама не запускает новый разбор. |
| Навигация и ввод | `/cancel`, меню в процессе, старые кнопки, двойной tap, свободный текст, неверная дата/место, фото вне режима, неподдерживаемый документ/голос. |
| Продуктовая полнота | Все включённые направления из таблицы проходят полный путь; проверяются и совместные сценарии, где нужны два участника. |
| Архив и приватность | Доступ к результатам старше первых 40, правильный владелец, общий сайт/бот, удаление результата и аккаунта, запрет доступа после удаления. |
| Отказы | Остановка бота во время генерации, отключение bridge, 429/timeout, повтор update, сбой отправки, восстановление из сохранённого результата. |
| Клиенты и содержание | Telegram iOS/Android/Desktop: читаемый длинный текст/диаграммы, фото/PDF, озвучка, Mini App, ввод с клавиатурой. Серия живых LLM-ответов с проверкой соответствия вопросу, картам, данным и выбранному мастеру. |

После локальных проверок — независимые code/security review; visual review при изменении Mini App/рендера; calc review при изменении расчётных контрактов. Production review — на этапе релиза. Итоговые PASS должны соответствовать текущей версии кода. Не заявлять готовность production на основании этого плана: текущая production-конфигурация и живые сценарии здесь не проверялись.

**6. ОТКРЫТЫЕ РЕШЕНИЯ**

1. Основной выбор интерфейса: этот план предполагает переписку плюс существующий Mini App. Если требуется абсолютно всё через сообщения, объём форм для Натала/HD, совместимости, обрядов и кабинета существенно увеличится.
2. Тестовые реквизиты и webhook ЮKassa для сквозной проверки без реального списания.
3. Конфликт двух уже созданных аккаунтов: подтвердить существующий upgrade и решить, нужен ли отдельный перенос. Это не препятствует доработке меню, диалога и продуктовых сценариев.
4. Актуальный набор включённых продуктов и тестовый Telegram-контур определить перед реализацией/живой приёмкой. Наличие кода или старого отчёта не подтверждает настройку BotFather и production-флагов.

Рекомендуемый первый пакет реализации: навигация и согласия, контракт безопасного продолжения диалога, повторяемый заказ ЮKassa и тестовый стенд. Затем завершать по одному пользовательскому пути с оплатой, результатом и восстановлением.
