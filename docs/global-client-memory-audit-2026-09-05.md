## Что проверено

Прослежен общий путь: согласие → захват сообщения → очередь extraction → извлечение и grounding → user_facts → ClientMemoryPack → контекст продукта. Прочитаны очистка, ручной ввод, захват совместных раскладов, очередь, настройки и тестовый стенд. Найдены вызовы общего контекста в чате, reading, intention-spread, photo-reading, daily-energy, натале, HD, нумерологии, обрядах и Telegram photo/matrix. Наличие вызова не доказывает работоспособность всего пользовательского сценария.

## Подтверждённые недостатки и риски

### M1 · P1 · Очередь не восстанавливает running после аварии

`src/lib/memory/extraction-jobs.ts:108`: claim выбирает только pending и переводит в running. Восстановления просроченных running в доступном коде src/scripts не найдено. Если процесс завершился после claim, failMemoryExtractionJob не выполняется, следующие проходы задачу не подберут.

Уверенность: высокая по коду; падение процесса с тестовой БД ещё не воспроизводилось. Для сравнения, очередь Memory Intelligence уже использует processing_at, восстановление через 10 минут и проверку владельца claim. Нужен аналогичный протокол для extraction, включая защиту от запоздалого старого worker.

### M2 · P1 · Очистка не атомарна и допускает ложный успех

`src/lib/memory/user-facts.ts:1481`: отмена/удаление jobs, удаление derived memory, tombstones, session memories, facts, reminders и отзыв согласия выполняются отдельно. Ошибки удаления jobs/derived и отзыва согласия подавляются. Endpoint может вернуть ok при неполной очистке.

`src/lib/memory/client-memory.ts:145` проверяет согласие до длительного извлечения. `user-facts.ts:580` при записи проверяет tombstones, но не согласие. Очистка не использует общий FACT_WRITE_LOCK_CLASS. Возможна последовательность: worker проверил согласие → очистка завершилась → worker записал ранее неизвестный факт, для которого tombstone отсутствует.

Уверенность: высокая в наличии дефектов синхронизации/обработки ошибок; конкурентный сценарий и фактическое восстановление данных требуют тестовой БД. Нужны единая транзакция очистки, согласованный lock/версия согласия и запрет устаревшей автоматической записи. Ручную запись необходимо сохранить как отдельный разрешённый путь.

### M3 · P1 · В совместном раскладе перепутана перспектива получателя

`src/lib/memory/capture-helpers.ts:92`: userMessage формируется как «Клиент: инициатор. Партнёр: второй участник». Этот же текст передаётся в recordTurn для обоих userId. Для второго пользователя описание клиента неверно.

Уверенность: высокая в ошибке входа extraction; какой конкретно ошибочный факт создаст LLM, не проверено. Нужен отдельный текст для каждого владельца и явное обозначение участника расклада, без предположения о романтических отношениях.

### M4 · P2 · Короткие реальные факты теряются

`src/lib/memory/client-memory.ts:113`: любое сообщение короче 8 символов отбрасывается. «Я женат», «Я вдова», «Мне 30» не доходят даже до очереди. Проверено вычислением действующего условия на этих строках. Следует отличать бессодержательное подтверждение от краткого факта; одного порога длины недостаточно.

### M5 · P2 · Ручные накопления превращаются в долг

`src/lib/memory/user-fact-input.ts:105`: вся категория money получает finance.debt. Прямой запуск production-функции validateUserSubmittedFact("Я накопил миллион рублей", "money") вернул predicateKey finance.debt. Это искажает смысл в поиске и производных состояниях. Нужна классификация по содержанию с нейтральным fallback в рамках существующих предикатов.

### M6 · P2 · Несуществующая дата проходит валидатор

`src/lib/memory/user-fact-input.ts:57`: проверяется только шаблон YYYY-MM-DD. Прямой запуск validateUserSubmittedFact("Переезд в Москву", "event", "2026-02-31") вернул эту дату как допустимую. Поведение дальнейшей записи в PostgreSQL не проверено. Нужна календарная проверка до SQL и понятная ошибка ввода.

### M7 · P2 · Фильтр запрещённых тем задевает обычные слова

`src/lib/memory/user-fact-input.ts:25`: поиск подстрок карт/рун и т. п. отбрасывает нерелевантные совпадения. Прямой запуск isQualityMemoryFact("Я люблю картофель") вернул false. Не нужно ослаблять защиту инструкций: исправить границы тематических совпадений и закрепить контрпримеры.

### M8 · P2 · Метрики не отражают фактический контекст

`src/lib/memory/client-memory-pack.ts:569`: selected_count вычисляется до сериализации. Serializer затем удаляет целые разделы при переполнении бюджета, но количество выбранных фактов не пересчитывается. `build-memory-context.ts:131` всегда указывает sourceType chat, включая другие продукты. Из-за этого сложно объективно оценивать качество памяти по продуктам.

Уверенность: высокая по потоку кода; необходим тест переполнения и проверка допустимых типов аналитики. Сериализация должна возвращать метрики именно отправленного контекста.

### M9 · P2 · Тестовый scorecard создаёт чрезмерную уверенность

`tests/memory-quality/run.ts`: извлечение тестируется на синтетическом JSON, поиск — с лексической заменой. `evals.ts:339` проверяет интеграции по наличию строк в исходниках; cross_user_leak проверяет наличие хотя бы одной строки WHERE user_id = $1 в файле. Это не проверка изоляции всех запросов или реальной работы разных продуктов.

Нужно оставить быстрые тесты и добавить поведенческие: два клиента с похожими именами, смена устройства/канала, падение worker, повторная доставка, purge во время extraction, отключение/повторное включение памяти, отсутствие релевантных фактов, недоступность embeddings, ручное исправление и устаревание данных.

## Дополнение: премиальность должна быть видна в действии

Уточнение пользователя: клиент должен видеть глобальную память как премиальную функцию через реальную пользу и функциональность. Это обязательная часть результата.

В интерфейсе уже есть MemoryMoments («Запомнила» / «Предлагаю запомнить»), MemoryAnchorSuggestion и кабинет с редактированием/подтверждением. Их следует развивать, не создавать ещё один несвязанный экран.

Дополнительные находки:

- M10 · P2: MemoryMoments опрашивает activity каждые 4 секунды, API допускает 180 запросов в час на аккаунт. При постоянном активном чате лимит расходуется примерно за 12 минут; несколько вкладок ускоряют исчерпание. Ответ 429 молча игнорируется. Нужны согласованные частота/лимит, пауза в скрытой вкладке и backoff по retryAfterSec.
- M11 · P2: MemoryMoments.act и MemoryAnchorSuggestion.decide при !res.ok молча возвращаются; сетевые исключения не обрабатываются пользовательским сообщением. - M13 · P1: upsertFacts подавляет ошибки отдельных upsertFact и возвращает только число успешных; processMemoryExtractionJobs затем завершает задачу как completed. Временный сбой записи может потерять часть фактов без retry. Нужен проверяемый результат частичной записи и идемпотентный повтор; отказ политики не считать технической ошибкой.

## Реализация

- Очередь: истекающая аренда, новый token при recovery, completion только текущим владельцем; задания захватываются непосредственно перед обработкой. Частичный retry использует сохранённый extraction_result и HMAC ledger, поэтому не вызывает повторное подтверждение уже применённого факта. Пустой/повреждённый ответ extractor становится retry, а не успешной потерей сообщения.
- Согласие: общий advisory lock для настроек, записи, удаления и derived rebuild. Исходное поколение передаётся от начала LLM операции; async jobs сохраняют его в серверном provenance. Profile/onboarding и HD также ожидают запись и передают исходный token. Старые задания без token не захватывают данные задним числом.
- Purge: одна транзакция отзывает согласие и очищает факты, summaries, очередь, activity, receipts, derived state и напоминания. Tombstones создаются в той же транзакции. Старый worker/rebuild не возвращает удалённое, даже после повторного включения.
- Ручное добавление: включение памяти и получение поколения атомарны. Отказ tombstone/смена памяти возвращают явный 409. Невозможные даты отвергаются, свободные финансовые сведения не становятся «долгом», «картофель»/«картограф» не отсекаются словом «карты».
- Короткие факты проходят и facade, и extractor. Оба пути joint capture описывают каждого участника с его позиции.
- Персонализация: сериализатор возвращает реально переданные факты и метрики после бюджета. Окончательная проверка consent + fresh выполняется после retrieval. Добавлен общий контекст для полных aura/palm отчётов; память не влияет на распознавание изображения/снимок и не подмешивается в aura другого человека.
- Клиент видит действительные состояния, источники, даты и цитаты, может искать, исправлять и удалять. Receipt означает только передачу факта при подготовке обращения — не доказательство его использования моделью. Хранятся id/version, а не копии персональных текстов; удалённые/изменённые версии скрываются.
- Сайт, мобильный webview и связанный Telegram используют тот же профиль. Telegram показывает режим, источники и сводку контекста, ведёт в управление памятью.
- Activity polling: 30 секунд, пауза в скрытой вкладке, abort, backoff и обработка 429. Ошибка действия видна, текст правки сохраняется. Cron extraction запускается каждую минуту с flock вместо пяти минут; запоминание остаётся асинхронным, точный срок зависит от очереди и AI-провайдера.
- Миграции 149–152 парные. schema.sql синхронизирован также с уже существующими 147/148: preflight обнаружил отсутствующие таблицы erasure/bot operations. Повторный schema-diff: PASS, 78 таблиц.

Новые regression cases покрывают late enqueue, ручную запись после purge, короткие реплики до extractor, ошибку провайдера, исходное согласие durable jobs и сохранённый extraction batch.

Playwright personal-memory.public: 3/3 PASS на 390 и 1280 px (источник/цитата, переданный контекст, поиск, ошибка сохранения с сохранением текста, retry, удаление). Данные API подменяются только в локальном тесте; внешний переход блокируется. Локальная dev-БД до миграций пишет предупреждение об отсутствующем erasure_requested_at при проверке синтетического JWT; это не служит доказательством production auth. DB ownership покрыт отдельными интеграционными тестами.

Полный harness, независимые code/security/visual/calc reviews и production проверки обязательны. Их итоговый verdict привязан к fingerprint релиза в harness-state, а не к промежуточной формулировке этого отчёта. До PASS выпуск не считается законченным.

Предварительная production проверка: app, async worker и Telegram service active; доступно 17 GB. Канонический deploy-prod.sh собирает committed HEAD, сохраняет env/runtime, строит staging, останавливает всех consumers перед миграцией и проверяет восстановление services. Сторонние изменения Yandex/tsconfig/local agent files не включаются в коммит.

Откат: canonical deploy автоматически восстанавливает предыдущий release при безопасном состоянии; после принятой новой работы применяется его forward-recovery guard. Добавленные DB поля совместимы со старой схемой чтения; down migrations разрешены только при остановленных app/worker и после согласованного отката кода. Не откатывать данные клиентов из snapshot поверх принятой работы.
